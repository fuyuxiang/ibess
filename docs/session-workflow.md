# 以场次组织现场监管

衡鉴按“评前准备 → 现场监管 → 收尾办理 → 归档”组织作业。现有事件识别、人工办理、证据保全与回放接口继续使用原链路；新流程为这些资料增加场次级检查、操作记录和归档版本。

## 岗位与入口

- 管理员：创建场次、绑定监测来源、标定区域与阶段方案，按需补充人员名单或启用人员身份核查。
- 监管人员：在业务工作台完成准备确认、启动、阶段推进、巡查交接、临时许可、结束和归档。
- 处置人员：办理分派给本账号的事件，不能修改场次方案或启动、结束、归档场次。
- 只读人员：查询业务资料，无写入或导出权限。

服务端独立检查岗位权限；所有操作记录使用登录账号和服务端时间。更新携带 `expected_version`，过期记录返回 409，需要刷新核对。

## 评前准备

1. 管理员在“现场配置 → 项目与场地”维护项目与评标室。业主、计划日期和位置为补充资料；需要工位能力时再登记工位。
2. 在“现场配置 → 现场资源”登记固定机位与拾音通道，选择默认方案，保存带说明的资源版本。需要时再展开区域标定，载入对应机位静态截图并绘制区域；图片留在本机浏览器，只保存归一化几何坐标。
3. 在业务“场次管理”新建场次，选择项目、评标室与现场资源版本。机位、区域和方案复制为本场独立配置，创建后直接进入同一场次的“评前准备”。
4. 默认使用“基础行为监管”，保留通话、拍摄、近距交流、资料递接和见证完整性场景，仍按独立评审与正常讨论阶段区分处理。工位与限制区域判断、出入核查需对应标定；基础方案不因缺少工位区或门线阻断开场。模型、采集服务和消费者须实际部署，方案选择不代表识别已就绪。
5. 需要工位离席和出入核查时，选用“完整现场监管”，必要检查才要求工位观察区和出入口线。管理员在本场“调整监测方案”保存并应用，一次事务提交方案、阶段快照和同步任务，不再逐格配置六阶段矩阵或另点应用初始阶段。S10 始终保留。
6. 监管人员确认场地巡检、通讯设备寄存与应急联络安排后开始监管；人员名单与全员核验默认不阻断。

现场资源只追加新版本，数据库拒绝改写或删除版本。资源更新不自动影响旧场次。草稿可明确载入同一组、同类型通道的新版本；原资源和旧区域保存到本场日志。物理来源或通道类型发生变化时需创建新场次，避免静默改变消费者授权范围。既有自定义六阶段方案不被升级覆盖，原方案接口与阶段历史继续保留。

开场检查继续验证评标室与物理监测源占用、业务绑定、视频来源、实际启用能力所需标定、初始阶段方案及必要人工检查。草稿不要求运行中的心跳；开始后仍须分别核对实时画面、录像与分析回执。未配置或未收到回执保持待核验，不视为正常。

## 按需准备人员资料与身份核查

人员操作统一位于业务场次“评前准备 → 人员资料（选填）”。带场次的旧人员链接跳转至对应准备页，无场次的旧入口返回场次列表选择现场，不再提供独立管理菜单。名单仍沿用评标室已有的到场事实和授权历史，进入时会核对所选场次、项目及评标室，避免切到其他现场。

默认“人员身份核查”为关闭：可以完全不填写人员资料，也可仅登记人员、岗位或工位后保存名单。没有身份依据的人员会如实保存为未核验，不伪造核验结果。关闭身份核查时，该场次的连续视觉分析不调用自动人脸匹配，工位与区域观察、基础行为规则和按工位登记的许可继续工作。

确需判断已识别人员是否属于本室授权名单时，由管理员在开场前明确启用“人员身份核查”。此时才要求有效名单、计划人数一致、全员核验及入场身份人工核对。照片管理与一对一核验从人员行打开；与当前登记照仍相符的既有关联可带入，新核验记录须明确选择。未匹配或模糊的人脸仍属于待核验，不能直接认定未授权。

名单、登记照或核验记录变化后需刷新核对，过期确认返回 409。核验关联与新授权版本同事务保存，历史版本、登记照和核验结果保留。保存选填名单也会记录办理账号及场次日志。资料接收授权仍需真实业务依据，涉及保密资料时填写保密依据编号。

身份选项仅可在开场前修改。已结束场次中的人员资料只读；准备中的场次不能改动同室另一进行中场次的名单。现有管理员、监管、处置与只读岗位的权限边界继续生效。

升级需执行 `0005_optional_identity`。新场次及存量草稿默认关闭身份核查；存量进行中和已结束的场次保留旧身份模式，原始核验、授权及归档资料不改写。未纳入场次流程的历史运行配置继续按既有行为执行；纳入时也保留其运行模式。

## 部署人员接入阶段消费者

服务消费者使用独立令牌及精确的项目、评标室、场次、来源范围，不使用浏览器管理员凭据。新安装的 `scripts/init_env.py` 同时生成随机令牌和 `config/phase-consumers.local` 摘要文件，初始范围为空，因此不授予任何场次访问权限。

日常页面不再导出部署范围 JSON。部署人员从运行中的 API 容器读取所选场次的全部启用通道，在项目根目录执行：

```bash
python3 scripts/configure_phase_consumer.py --session-id <场次UUID>
```

已有安装在本机 `.env` 增加：

```dotenv
PHASE_CONTROL_CONSUMERS_PATH=./config/phase-consumers.local
```

`--scope-file` 仍兼容既有准确作用域文件。新命令以参数数组调用容器内只读模块，验证返回的场次和完整四项范围；多通道范围一次校验、原子保存，不使用通配符。

本工具读取 `.env` 中的 `PHASE_CONTROL_TOKEN_EVENT_SERVICE`，只保存摘要与去重后的精确范围；不输出原始令牌、不执行配置值中的命令。文件权限为 600，并被 Git 和源码打包忽略。添加范围后重新创建 API 容器加载文件：

```bash
docker compose -f docker-compose.yml -f deploy/linux/docker-compose.linux.yml up -d --force-recreate api
```

识别消费者必须运行并实际读取、应用当前版本，再提交应用回执。值守页面区分待确认、部分应用、缺少素材、应用失败与已应用。没有回执时不会展示已应用；如新增其他必需消费者，需分别维护其配置，不能直接减少服务端必需集合。

## 管理中心的低频配置

现场配置只维护可复用资源和项目场地，场次创建与准备在业务工作区完成。规则列表聚焦名称、风险和启停；技术标识、版本、回执、绑定与留痕收进详情，配置修改自动产生版本，已有显式版本调用仍兼容。运行保障默认显示异常与待核验来源，可切换全部；无拾音来源时收起语音状态列。维护入口不增加日常导航。

## 现场值守

- 阶段按入场签到、宣读纪律、初步评审、详细评审、澄清讨论、收尾宣读顺序推进，使用管理员保存的方案。
- 巡查和交接记录保留办理内容、账号、时间，进入场次记录及归档快照。
- 临时许可支持业务交流、资料递接、业务拍摄、应急通信和休息，可限定工位与结束时间。许可作为不可变业务事实，与新阶段快照引用一并提交；视觉规则通过原有数据库上下文读取并校验范围和有效时间。许可不改写既有告警或人工结论。
- 待核查线索进入原事件闭环：核查认定、分派处置、反馈、人工复核与事件归档。证据未完整保全时继续使用原有缺失说明要求。
- 需要补充原音时，从事件“关联资料 / 扩展时段”选择原音关联，再按需打开“补充音频资料”。核对录音所属评标室及实际采集时间，完成后明确关联时间重叠的录音；上传和分析本身不会自动替换事件证据。身份识别参数与部署说明从管理员“运行保障 → 部署与识别参数维护”按需进入。录音上传、转写与补充分析继续从事件补证打开，后台接口保留。

## 现场结束与归档

登记现场结束时可保留未办结事件，现场状态与办理状态分别记录。已纳入新流程的场次不能通过旧启动、停止接口绕过检查。

归档要求：

1. 现场已结束至少 90 秒，为异步结果与后滚录像留出收集时间。
2. 场次所有预警事件已核查办结。
3. 确认资料物品交接、人员离场与场地复核。
4. 存在覆盖待核验区间或媒体保全缺口时，填写不少于 10 字的核查说明；说明不会将缺失媒体改为“已保全”。

90 秒是当前流程的收集缓冲，不是所有消费者完成的保证。归档后新增事件、事件办理变化、保全状态变化或补充记录会使内容指纹不一致，显示“需补充归档”。新的归档快照链接上一版，原版本保持可查。监管档案默认只列有正式归档记录的场次；既有阶段性查阅记录仍可通过原报告链接读取，并明确标为历史查阅记录。

日常页面撤去手工生成查阅快照及 JSON 导出操作。监管人员和管理员可导出监管报告或事件证据包，原有导出鉴权及留痕继续有效。后台查阅快照、历史报告、JSON 接口和离线视频任务保留，供既有依赖调用。

既有场次保留原始数据，可由管理员在场次工作区“纳入监管流程”；运行中或已结束的历史场次不会被重置成草稿。
